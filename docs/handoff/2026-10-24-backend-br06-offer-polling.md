# [pmart-clients → pmart-backend] BR-06 추가 질문: `GET /offers` 폴링 간격

- 회신 대상: `pmart-backend/docs/handoff/2026-10-24-clients-reply-high.md` 의 BR-06
- 기준 커밋: pmart-backend `c609a4d`, `contracts/openapi/delivery-dispatch-service.yaml` `listMyOffers`
- 클라이언트 상태: BR-06 은 `AGREED(부분, e817184, 빌드 미검증)` 으로 기록했다. 목 구현에서는 폴링 간격을 설정값으로 두고 하드코딩하지 않는다.

## 질문 배경
- 회신에 따르면 푸시·SSE 가 정해지기 전에는 폴링을 쓰고, 폴링 간격은 계약으로 정하지 않았다.
- 제안 응답 제한은 1분이다(`expiresAt = sentAt + 1분`).
  - 간격이 길면 라이더가 제안을 늦게 보고, 응답할 시간이 줄어든다.
  - 간격이 짧으면 운행 중인 라이더 전원이 계속 호출하게 된다.
- 게이트웨이 처리율 제한(잠정값, `application.yml`)은 인증 사용자 기준 `replenish-rate: 20`, `burst-capacity: 40` 이다. 라이더 한 명의 폴링이 이 한도를 넘을 일은 없다. 다만 위치 전송 같은 다른 호출과 같은 버킷을 쓰는지는 확인이 필요하다.
- 클라이언트가 간격을 임의로 정하면 라이더 수 × 호출 빈도로 delivery-dispatch 부하가 정해진다. 그래서 서버 쪽 기준을 받고 싶다.

## 질문
1. **기본 폴링 간격**: 운행 중이고 신규배차가 ON인 라이더가 `GET /offers` 를 몇 초마다 호출하면 되는가?
2. **상태별 간격**: 아래 상태마다 간격을 다르게 해야 하는가?
   - 신규배차 OFF이거나 운행 종료 → 폴링 중지로 이해하고 있다. 맞는가?
   - 진행 중인 배송이 있을 때. 연속 배차 최대 3건, 하나씩 배달 설정 등에 따라 달라지는가?
   - 앱이 백그라운드에 있을 때. OS 제약 때문에 짧은 간격의 백그라운드 폴링은 사실상 어렵다. 백그라운드에서는 푸시 전까지 제안을 놓칠 수 있다는 점을 업무상 허용하는가?
3. **서버가 간격을 내려줄 수 있는가**: 응답에 권장 간격(예: `pollAfterSec`)을 넣거나, 다른 설정 조회로 받을 수 있는가? 그러면 운영 중에도 앱을 배포하지 않고 조정할 수 있다. 어렵다면 클라이언트 원격 설정값으로 둔다.
4. **처리율 제한**: `GET /offers` 폴링이 인증 사용자 버킷(20/s, burst 40)을 위치 전송 등과 같이 쓰는가? 별도 한도를 둘 계획이 있는가? 클라이언트는 429를 받으면 `Retry-After` 를 따른다.

## 클라이언트 처리안 (회신 전 목 구현 기준)
- 간격은 설정값 하나로 둔다(목 기본값은 임시이며 업무 확정값이 아니다).
- 앱 실행, 포그라운드 복귀, 알림 탭, 운행 시작 시에는 간격과 관계없이 즉시 조회한다.
- 신규배차 OFF이거나 운행 종료면 폴링을 멈춘다.
- 응답이 실패하면 지수 백오프로 재시도하고, 429는 `Retry-After` 를 따른다. 조회 실패를 "제안 없음"으로 표시하지 않고 "연결 확인 중"으로 표시한다.
