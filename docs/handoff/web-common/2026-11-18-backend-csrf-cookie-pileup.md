# [pmart-clients → pmart-backend] 요청: 백오피스 CSRF 쿠키가 쌓여 431 — 만료 시간을 붙여 주세요 (2026-11-18)

- 보낸 앱: web-common (`web/core` 직원 로그인 — backoffice·hr-backoffice·mfc-backoffice·rider-backoffice 모두 씀, PC 1)
- 받는 백엔드 영역: platform (employee-auth-service, ADR-0059 refresh 쿠키)
- 계기: PC 2 LAN 시험(2026-11-18, `docs/worklog/hr-backoffice/2026-11-18.md` 10:55, PR #111) — 인사팀 백오피스 일반 창에서 **431(요청 머리말이 너무 큼)**, 사이트 데이터를 지우자 로그인됨.
- 확인 방법: 백엔드 코드 읽기만(`services/employee-auth-service/.../api/RefreshCookies.java`). 브라우저 쿠키 개수를 실제로 세지는 않았다 — 원인은 추정이다.

## 1. 지금 모양 (`RefreshCookies`)

| 쿠키 | 이름 | Path | Max-Age | 실리는 요청 |
|---|---|---|---|---|
| refresh | `__Secure-pmart_ea_rt` | `/api/v1/employee-auth/tokens/refresh/{sessionId}` | 없음 | 그 세션의 갱신 요청만 |
| CSRF | `__Secure-pmart_ea_csrf_{sessionId}` | `/` | 없음 | **그 호스트의 모든 요청** |

- CSRF 쿠키는 세션마다 이름이 달라(탭·앱끼리 덮어쓰지 않게 — 의도대로) 로그인할 때마다 하나씩 생긴다.
- 지우는 때는 로그아웃(`clear`) 하나뿐. 세션이 무활동·최대 시간으로 끝나거나, 탭을 닫거나, 앱이 로그아웃을 부르지 못하면 남는다. Max-Age 가 없어 브라우저 세션 쿠키인데, 크롬은 "이전 세션 이어서"면 창을 닫아도 지우지 않는다.
- 쿠키는 포트를 가리지 않는다 — LAN 의 백오피스 4개(443·8444·8445·8446)가 같은 호스트 `192.168.0.40` 이라 한곳에 쌓이고, Path=`/` 라 모든 앱의 모든 요청에 실린다.
- 하나가 약 100바이트 안팎이면 수십 개 → 수 KB. 게이트웨이(또는 앞 Nginx)의 요청 머리말 한도를 넘으면 431.

## 2. 요청

| # | 요청 | 왜 |
|---|---|---|
| C1 (추천) | CSRF 쿠키에 **Max-Age** 를 붙여 주세요 — 세션의 최대 만료(`maxExpiresAt`)까지 남은 시간. refresh 쿠키도 같게 하면 좋다 | 끝난 세션의 쿠키가 저절로 사라진다. 앱 코드는 그대로(쿠키 이름·Path·읽는 법 같음) |
| C2 (C1 이 어렵다면) | CSRF 값을 쿠키가 아니라 티켓 교환 응답 본문으로 주고 앱이 탭 저장소에 둔다 | 쿠키가 아예 안 쌓인다. 대신 계약·`web/core` 변경 — PC 1 이 함께 고친다 |

- 앱이 혼자 지우지 않는 이유: CSRF 쿠키는 JS 로 지울 수는 있지만, 같은 호스트의 다른 앱(포트)·다른 탭이 아직 쓰는 세션인지 앱이 모른다. 잘못 지우면 그 세션의 갱신이 403 이 된다.
- 함께 알려 주세요: LAN 게이트웨이·Nginx 의 요청 머리말 한도(지금 몇 KB 에서 431 인지). 한도를 올리는 것은 근본 해결이 아니라 C1 과 같이 보는 것이 좋겠다.

## 3. 앱 쪽

- C1 이면 앱 변경 없음 — 배포 뒤 PC 2·3·5 에 "사이트 데이터 한 번 지우기"만 안내한다.
- C2 면 계약이 나온 뒤 `web/core` `employeeAuth.ts`(티켓 교환·갱신)를 고치고 네 앱을 다시 빌드한다.
