# 요청 BR-112·BR-113 — 할인 탭 할인율 버튼, 랭킹 탭 "최근 3시간 클릭 많은 상품"

- 보낸 앱: customer-app (PC 1)
- 받는 백엔드 영역: platform (search-service · storefront)
- 계기: 사용자 2026-11-26 레퍼런스 캡처 — 홈 할인 탭 위에 [전체 · 50% 초과 · 40% · 30% · 20%], 랭킹 탭 "다른 사람들도 많이 눌러 봤어요 · 최근 3시간 클릭이 많은 상품". 사용자 결정: "요청서 쓰고 그동안은 목으로만".

## 지금 앱
- 할인 탭: 할인 목록은 `GET /search/products?onSale=true`(0.8.0)·정렬 `DISCOUNT_RATE`(0.9.0). 할인율 **이상**으로 거르는 조건이 없어 버튼은 **목 모드에서만** 보인다(앱 `ProductQuery.minDiscountRate` — 실서버 저장소는 보내지 않는다).
- 랭킹 탭: 위 배너(HOME_TOP) → "다른 사람들도 많이 눌러 봤어요"(**목 모드만**, 목 데이터 = 인기순 앞 6개) → "꼼꼼하게 선정한 베스트"(`sort=POPULAR` 카테고리별, 끝까지 이어 받기).

## 요청
### BR-112 할인율 조건 (search)
- R1 `GET /search/products` 에 `minDiscountRate`(정수 %, 1~99) — 대표 SKU 기간 할인율(`discountRatePercent`, 0.6.0 과 같은 값)이 그 이상인 상품만. `onSale=true` 와 함께 쓴다(없으면 400 이어도 된다).
- R2 버튼 구간: 레퍼런스는 "50% 초과 / 40% / 30% / 20%". 앱은 "40%" = 40% 이상으로 본다. "50% 초과"는 `minDiscountRate=51` 로 보내면 되는지, 구간(이상~미만)이 필요하면 `maxDiscountRate` 도 — **Q1**: 구간이 맞는지(40% 버튼에 55% 상품이 나와도 되는지).
- R3 `total` 은 거른 수.

### BR-113 최근 클릭 많은 상품 (storefront 또는 search)
- R1 목록 API — 지금 주소 센터에서 파는 상품 중 최근 N시간(레퍼런스 3시간) 상세 조회가 많은 순, 6개(또는 `limit`). 응답은 검색 항목과 같은 모양(카드 그림·가격·할인·평점)이면 앱이 그대로 그린다.
- R2 집계 시각(`aggregatedAt`) — 화면에 "기준" 시각을 적을 수 있게(레퍼런스 베스트 목록의 "11월 26일 15시 기준 ⓘ" 도 같은 값이면 좋다).
- R3 상세 조회 기록은 앱이 따로 보내지 않아도 되게(상품 상세 `GET` 으로 센다) — **Q2**: 서버에서 셀 수 있는지, 앱이 이벤트를 보내야 하는지.
- 순위 변동(▲6·▼1·NEW)은 BR-110 과 같은 값이면 함께.

## 회신 받으면 앱이 할 것
- BR-112: 실서버 저장소에 `minDiscountRate` 전달, 버튼을 실서버에서도 보이기.
- BR-113: 목 대신 API, 실서버에서도 구획 보이기(빈 목록·실패면 구획을 비운다 — 지어낸 순위 없음).
