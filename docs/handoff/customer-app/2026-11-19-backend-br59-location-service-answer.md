# 답 — BR-59 회신의 질문: 현재 위치를 주소로 바꿀 때 쓰는 서비스

- 보낸 앱: customer-app (PC 1)
- 받는 백엔드 영역: platform (위치기반서비스 이용약관 제6조), 참고 delivery (delivery-serviceability 역지오코딩)
- 원 문서: 회신 `../pmart-backend/docs/handoff/clients/customer-app/2026-11-19-reply-br59-first-run-consents.md` "앱이 알려 줄 것"
- 요청: 사용자 2026-11-19 "백엔드 질문에 답하기 … 해줘"

## 답
1. **좌표 → 주소: 카카오 로컬 API(주식회사 카카오), PMart 서버를 거쳐서.** 앱은 카카오를 직접 부르지 않는다.
   앱 → `GET /api/v1/address-reverse-geocodes?lat=&lng=`(delivery-serviceability) → 서버가 카카오 로컬 호출(ADR-0023, 지도 핀 화면이 이미 이렇게 쓴다).
   그러니 휴대폰 좌표를 받는 제3자는 **주식회사 카카오(카카오 로컬)** 하나다.
2. **지도 표시: 카카오맵 SDK(주식회사 카카오, Android `kakao_map_sdk`).** 주소 입력의 지도 핀, 배송현황 라이더 지도에 이미 쓴다.
   현재 위치로 찾은 뒤 지도를 그 자리로 옮기면 지도 타일 요청이 카카오로 간다.
3. **휴대폰 위치 수집: Android 위치 서비스**(Google Play 서비스 위치 — 라이더앱이 쓰는 `geolocator` 라이브러리와 같은 방식).
   - 사용자 승인(2026-11-19)으로 고객앱에 넣었다 — 처음 실행 주소 화면(레퍼런스 2-4)의 "현재 위치로 찾기".
   - 위치 약관 동의를 서버에서 확인한다. 회원은 `/me/consents`, 비회원은 `/device-consents` 로 본다.
   - 동의가 없으면 묻고 기록한 뒤에만 OS 위치 권한을 묻는다. 거부하면 5-2 "위치 공유 설정" 안내를 띄운다.
   - 위치는 누를 때 한 번만 읽고 앱에 저장하지 않는다.
   - 찾은 주소는 고객이 확인해야 배송지가 된다. 배송지 좌표는 지금처럼 고객 핀 또는 서버 지오코딩이다.

## 질문 1개(위치정보 관점)
- Q1. `/address-reverse-geocodes` 는 **좌표를 URL 쿼리**로 받는다(`lat`·`lng`). 이렇게 하면 게이트웨이와 서비스 추적 기록(`http.url`)에 고객 현재 위치가 남는다.
  `/address-geocodes` 의 주소는 같은 이유로 내부 경로가 본문으로 바뀌었다(PC 1 검토 H3, 2026-11-13).
  이제 "현재 위치로 찾기"가 이 경로로 고객의 실제 현재 위치를 보낸다(지도 핀 화면도 같은 경로). 이 경로도 본문(POST)으로 바꾸거나, 추적 기록에서 쿼리를 지울지 정해 달라. 바뀌면 앱이 따라간다.
