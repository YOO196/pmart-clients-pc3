# [pmart-clients → pmart-backend] 고객 휴대폰 번호(가입·변경·배송지 자동 채움), 내 환불 목록 요청 (BR-32·BR-33) (2026-10-31)

- 관련: `customer-service.yaml` profile 태그(`GET /me`, `POST /me/profile-changes`), `claim-service.yaml`(`GET /claims/{claimId}/refunds`)
- 사용자 결정(2026-10-31):
  1. 비회원도 배송지를 반드시 등록할 수 있어야 한다. 고객앱은 `/guest-delivery-addresses` 로 반영했다.
  2. Google 로그인은 휴대폰 번호를 주지 않는다. 그래서 **회원가입 직후 휴대폰 번호를 입력받는다.**
  3. 가입 때 받은 정보로 배송지의 받는 분·연락처를 자동으로 채우고 싶다.
  4. 마이에 휴대폰 변경·환불 관리를 둔다.

## 1. 휴대폰 번호 저장 — `POST /me/profile-changes` 구현 (BR-32, 필수)
- 현황: LAN 에서 `ProfileController` 가 프로필 변경을 **501**(인터페이스 default)로 돌려준다. `GET /me` 의 `phoneMasked` 를 채울 경로가 없다.
- 고객앱(반영됨):
  - 가입 직후(`AuthResult.newAccount=true`) "휴대폰 번호 등록" 화면을 띄운다.
  - 마이 → "휴대폰 번호" 에서 바꾼다.
  - 요청은 `{phone}` 이다(숫자만, 01X 로 시작하는 10~11자리. 화면 검증일 뿐 최종 검증은 서버). `Idempotency-Key`, `X-Expected-Version`(Profile.version) 을 붙인다.
  - APPLIED 면 저장됨이다. ACCEPTED 면 `GET /me/profile-changes/{requestId}` 로 확인한다.
  - **501 이면 "아직 준비 중"으로 안내하고 "나중에 하기"로 가입을 마치게 했다**(가입을 막지 않는다).
- 요청:
  - phone 변경을 구현해 달라. 형식 검증은 400 VALIDATION_FAILED, 버전 충돌은 409 VERSION_CONFLICT.
  - 저장 뒤 `GET /me` 의 `phoneMasked` 를 채워 달라.
  - 본인확인(SMS)은 업무 문서상 미정이라 앱은 하지 않는다. 확인 안 된 번호라는 점을 서버가 따로 표시할지는 백엔드 판단에 맡긴다.

- 추가(2026-10-31, 사용자 요청): 마이에 **"내 정보"**(이름·휴대폰 번호)를 두었다. 가입 직후 화면도 같다.
  - 계약 Profile 에 실명 필드가 없어서 **이름은 `nickname`(최대 30자)으로 보낸다**. `{nickname?, phone?}` 중 바뀐 항목만 보낸다.
  - nickname 을 이름(받는 분 기본값)으로 써도 되는지, 아니면 별도 `name` 필드가 필요한지 확인해 달라.

## 2. 배송지 받는 분·연락처 자동 채우기 (BR-32 후속, 결정 필요)
- 문제: `GET /me` 는 가린 번호(`phoneMasked`)만 준다. 그래서 주소 추가 화면의 연락처를 채울 수 없다. 실명도 없다(nickname 만 있음).
- 제안(택1, 백엔드·팀 결정):
  - (a) **본인 조회에 한해 가리지 않은 연락처**를 주는 필드나 경로를 둔다. 예: `GET /me/contact` → `{receiverName?, phone}`. 주소 추가 화면을 열 때만 부르고 로그에 남기지 않는다.
  - (b) 업무 문서 "수령 기본정보"(Commerce §고객정보)로 **기본 수령인(이름·연락처)** 을 저장·조회하는 경로를 둔다. 첫 배송지나 가입 때 입력한 값으로 채운다.
- 앱은 어느 쪽이든 **고칠 수 있는 기본값**으로만 채운다. 받는 분이 가입자 본인이 아닐 수 있기 때문이다.

## 3. 내 환불 목록 (BR-33)
- 현황: 환불 조회는 클레임 하나 단위(`GET /claims/{claimId}/refunds`)뿐이다. 고객의 클레임·환불을 모아 보는 목록이 없다. 주문 상세의 `claims` 는 아직 빈 배열이다.
- 요청: `GET /me/refunds`(또는 `GET /claims?mine`) 처럼 본인의 취소·반품 클레임과 환불 상태를 최근 순·커서로 주는 경로.
  - 필드 예: claimId, orderId, type, 상태, 환불 금액, 환불 상태(PG 성공 전 "완료" 아님), 기준 시각
  - 그때까지 앱은 마이에 "환불 관리"를 만들지 않는다. 목록을 그릴 근거가 없어서다.

## 4. 고객 비밀번호 변경 (확인)
- 사용자가 마이에 "비밀번호 변경"을 요청했다.
- 계약의 `POST /auth/password-changes` 는 **운영자 전용**이다. 고객은 소셜 로그인만 쓰고, 업무 문서상 자체 비밀번호 가입은 미도입이다.
- 고객 비밀번호를 도입할 계획이 없으면 앱은 이 메뉴를 만들지 않는다. 계획이 있으면 알려 달라.
