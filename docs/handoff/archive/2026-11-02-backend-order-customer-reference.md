# [pmart-clients → pmart-backend] 질문: 주문이 참조하는 고객 데이터(주소·수령인·연락처)의 불변성 보장 (BR-37) (2026-11-02)

- 관련: `order-service.yaml`(`OrderDraftCreate.shoppingAddressId`·`contact.phoneRef`, `Order`), `customer-service.yaml`(`PATCH /me/addresses/{addressId}` "확정 주문의 주소는 변경되지 않음", `DELETE /me/addresses/{addressId}`), ADR-0009(이벤트·사본에 개인정보 원문 금지), BR-32(본인 연락처·기본 수령정보)
- 성격: 계약 공백이 아니라 **보장 범위 확인 질문**. 고객앱의 주문 내역·취소·반품 화면이 "주문 당시 주소·수령인"을 어디서 읽어야 하는지에 달려 있다.
- 우선: 중간. 지금 당장 막힌 화면은 없다. 다만 주문 내역에 배송지를 보이기 시작하면(다음 작업) 바로 부딪힌다.

## 1. 읽은 것 (읽기 전용 확인, 2026-11-02 백엔드 HEAD 375b888)
- order-service `customer_order` 는 `account_id` 와 `shopping_address_id` 만 저장한다. 주소 원문·수령인 이름·연락처 컬럼이 없다. 초안(`order_draft`)도 같다.
- 결제 진입(`CheckoutService.start`)은 customer-service 를 부르지 않는다. 고객 검증(구매 가능·쇼핑 주소 판정·첫 구매)은 초안 생성(`DraftService.create`) 때 한 번 한다. 사가 본문의 고객 정보는 `customerRef`(계정 ID) 하나다.
- customer-service `customer_address` 는 `address_id` 당 한 행이며 `version`·`updated_at` 으로 **제자리 수정**한다. 이력·스냅샷 테이블이 없고 `deleted_at` 도 없다(물리 삭제로 보인다).
- 계약 `PATCH /me/addresses/{addressId}` 요약은 "주소 수정 (확정 주문의 주소는 변경되지 않음)". `DELETE` 는 "현재 쇼핑 주소면 INVALID_STATE" 만 막는다.

## 2. 질문
1. **"확정 주문의 주소는 변경되지 않음"은 어떻게 보장되나?**
   - 주문이 `shopping_address_id` 만 들고 있고 주소 행은 제자리 수정이므로, PATCH 뒤 그 ID 로 조회하면 바뀐 값이 나온다. 보장이 (a) 아직 미구현인지, (b) 다른 서비스(예: delivery-service 배송 지시)가 확정 시점에 사본을 뜨는 것인지, (c) 주문에 쓰인 주소는 PATCH 자체를 거절하는 것인지 알려 달라.
   - (b)라면 고객앱이 "주문 당시 배송지"를 읽을 **고객용 API** 가 무엇인지. `GET /orders/{orderId}` 에 배송지 사본(마스킹 가능)을 둘 계획이 있는지.
2. **확정 주문·미결 클레임이 참조하는 주소를 DELETE 할 수 있나?**
   - 지금 규칙은 "현재 쇼핑 주소"만 막는다. 배달 중이거나 반품 회수 예정인 주문의 주소가 지워지면 참조가 끊긴다. 막을 계획인지, 소프트 삭제로 바꿀 계획인지.
3. **수령인·연락처의 주문 시점 고정**
   - 배송 분쟁·반품 회수에 대비해 수령인 이름·연락처를 주문 시점 값으로 고정해야 하는지는 업무 결정이다. `contact.phoneRef` 가 참조라면 그 참조가 가리키는 값(안심번호 등)은 주문 뒤 바뀌지 않는가? BR-32 회신과 함께 정리해 달라.
4. **구매 가능 계정 검증 시점**
   - 초안 생성 때만 확인하고 결제 진입(견적 유효 시간 안)에는 다시 보지 않는다. 그 사이 계정이 정지되면 결제가 통과한다. 의도된 허용인지, 결제 진입에서 한 번 더 볼 계획인지.

## 3. 고객앱 쪽 전제 (회신 전까지)
- 주문 내역·클레임 화면은 주소 **원문을 앱에 저장하지 않는다.** 서버가 주는 값만 보인다(ADR-0009 와 같은 원칙).
- 주문 상세에 배송지를 보일 때 `shoppingAddressId` 로 `GET /me/addresses/{addressId}` 를 부르면 "현재 값"이지 "주문 당시 값"이 아니라는 점을 안다. 그래서 회신 전에는 주문 상세에 배송지를 **보이지 않는다**(잘못된 값을 확정처럼 보이지 않기 위해).
- 주소가 삭제된 주문(404)은 "배송지 정보 없음"으로 두고 0·빈값으로 꾸미지 않는다.

## 4. 바라는 것
- 1·2 는 보장 방식과 고객용 조회 경로, 3·4 는 결정만 있으면 된다. 계약 변경이 생기면 `order-service.yaml` `Order` 에 배송지 사본 필드를 어떻게 둘지(마스킹 수준 포함) 함께 알려 달라.
