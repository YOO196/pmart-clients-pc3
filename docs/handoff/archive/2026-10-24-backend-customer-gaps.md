# [pmart-clients → pmart-backend] 고객앱 계약 공백 요청 (BR-13~18, 6건)

- 보낸 쪽: pmart-clients 담당 (Flutter 앱 customer/rider/mfc + React backoffice)
- 기준 커밋: pmart-backend `85269ee` (계약은 `f4dd171` 이후 변경 없음)
- 원본 목록: `pmart-clients/docs/backend-requests.md` BR-13~18
- 계기: 고객앱 화면을 설계하면서 업무 문서(Commerce)의 표시 요구와 계약을 대조했다. 이 6건은 업무 문서에 근거가 있지만 계약에 경로나 필드가 없다.
- 업무 문서에 없는 기능(검색어 교정, 카테고리 상위 그룹 등)은 요청하지 않았다.
- 클라이언트는 회신 전까지 목(mock)으로만 구현하고, 계약에 없는 경로는 호출하지 않는다.
- 회신 요청: 항목마다 **수용 / 대안 / 보류**와, 계약에 반영한 커밋 SHA. 아래 경로·필드 이름은 예시다. 백엔드가 정하면 그대로 따른다.

## BR-13 배송 방식별 가능 여부·불가 사유·예상시간·배달팁 (중간)
**근거**
- Commerce :1552 표시 항목: 한집/알뜰/예약 가능성, 예상시간, 배달팁, 오늘/내일 1시간 슬롯, 정원/마감, 미설정 사유.
- Commerce :1524, :1530: 권역 밖, 휴무, 정원 소진, 운영 제한, 설정 확인 중, 조회 실패를 각각 구분해 안내한다.
- Commerce :1520: 00:00~08:00에는 실제 배송을 하지 않는다. 그 시간에도 08:00 이후 슬롯은 예약할 수 있다.

**현황**
- `delivery-serviceability` `GET /delivery-conditions` 는 제공하는 방식 목록(`deliveryModes`), 중량·부피 상한, `timeRestriction` 만 준다.
- `delivery-capacity` `GET /slots` 는 예약 슬롯만 다룬다.
- 다음 값을 받을 곳이 없다:
  - 지금 한집·알뜰을 쓸 수 있는지
  - 쓸 수 없을 때의 사유(심야, 휴무, 정원, 미설정)
  - 즉시 배송의 예상 소요시간 범위
  - 방식별 배달팁(기본 금액, 적용 금액, 사유)

**요청**
1. 주소(또는 `mfcId`)와 장바구니 기준으로 방식별 상태를 주는 조회. 예:
   `{ mode, availability, unavailableReason, etaMinutes: {min, max}, deliveryTip: {base, applied, reason} }`
2. 심야에는 서버가 "예약만 가능"과 가장 빠른 도착 슬롯을 판정해서 준다.

**클라이언트 원칙**
- 기기 시계로 심야 여부를 판단하지 않는다.
- 미설정(`NOT_SET`)을 "불가"나 "무제한"으로 바꾸지 않는다.
- 조회 실패를 "배달 불가"로 표시하지 않는다.

## BR-14 견적의 최소주문 부족액과 첫 구매 상태 (중간)
**근거**
- Commerce :1706: 최소주문 미달이면 부족액과 불가 품목·슬롯 사유를 표시한다.
- Commerce :2821: 최소 주문 15,000원은 오퍼·프로모션 후, 쿠폰 전 상품액으로 판정한다. 배달팁과 봉투값은 넣지 않는다.
- Commerce :1490-1512: 첫 구매 무료는 네 가지 상태로 표시한다(적용 예상 / 다른 주문에서 적용 확인 중 / 적용 확정 / 적용 불가).

**현황**
- `order-service` `Quote` 에는 `minOrderSatisfied`(boolean)와 `deliveryTipReason`(`STANDARD | OVER_30000 | FIRST_PURCHASE | NONE`)만 있다.
- 부족액이 없어서 "N원 더 담아 주세요"를 서버 값으로 표시할 수 없다.
- 첫 구매 무료의 네 가지 상태도 없다.
- `cart-service` `Cart.selectedItemAmount` 는 "견적 아님"으로 정의돼 있다. 그래서 장바구니 화면에는 최소주문이나 배달팁을 보여 줄 서버 값이 없다.

**요청**
1. `Quote` 에 최소주문 기준액과 부족액을 추가한다(예: `minOrderAmount`, `minOrderShortfall`).
2. `Quote` 에 첫 구매 상태 enum을 추가한다(예: `firstPurchaseBenefit: EXPECTED | CHECKING_OTHER_ORDER | CONFIRMED | NOT_ELIGIBLE`).
3. 장바구니 단계 표시 방식을 정해 준다:
   - 장바구니 화면에서 최소주문 미달과 예상 배달팁을 서버 값으로 받을 경로를 둘지
   - 아니면 주문서(초안 생성) 진입 뒤에만 표시할지
   - 후자라면 장바구니에서는 금액 조건을 표시하지 않는다.

**확인 요청**
- 30,000원 무료배송을 판정하는 상품액 정의가 업무 문서 안에서 두 가지로 적혀 있다.
  - Commerce :1621: "기본단가×수량"
  - Commerce :2857, :2760: "오퍼·프로모션 후, 쿠폰 전"
- 계약의 `Quote.itemAmount` 설명은 후자를 따르고 있다. 어느 쪽이 정본인지 확인을 부탁한다.

## BR-15 반품·교환 자격과 사유별 증빙 요건 (중간)
**근거**
- Commerce :1990 / OMS :336 `[확정 정책]`
  - 일반 교환·반품: 실제 수령 후 7일 이내
  - 신선식품: 수령 후 24시간 이내
  - 하자·오배송·광고와 다른 상품의 교환: 수령 후 3개월 이내, 또는 그 사실을 안 날부터 30일 이내
- Commerce :1986: 접수할 때 품목, 수량, 사유, 사진을 함께 받는다.

**현황**
- `claim-service` 에 `ClaimReason` enum(10종)과 `POST /claims` 가 있다.
- 접수 전에 품목별로 다음을 조회할 경로가 없다:
  - 반품·교환이 가능한지
  - 불가하다면 그 사유(기한 경과, 이미 신청함, 신선식품 변심 등)
  - 마감 시각
- 리뷰에는 같은 성격의 `GET /me/review-eligibilities` 가 있다.
- 사유별 증빙 요건이 계약에 없다: 사진이 필수인지, 사진 개수, 상세 사유가 필수인지, 글자 수.

**요청**
1. 주문 품목별 자격 조회. 예:
   `GET /me/claim-eligibilities?orderId=` → `[{ orderLineId, claimType: RETURN|EXCHANGE, eligible, ineligibleReason, deadline, maxQty }]`
2. 사유별 증빙 요건. 예: `{ reason, photoRequired, photoMin, photoMax, detailRequired, detailMaxLength }`
   - 첨부 업로드 방식 자체는 BR-07에서 다룬다.

**클라이언트 원칙**: 수령 시각으로 기한을 직접 계산하지 않는다. 서버가 준 자격과 마감만 표시한다.

## BR-16 고객 배송 문의 접수 (중간)
**근거**
- Commerce :1986: 배송 중이거나 완료된 주문에 대해 지연·오배송·파손·품질·누락·미수령·기타 문의를 받는다.
  - 오배송 문의에서는 원주소와 전달 사진을 확인하게 하고, 라이더 연락과 채팅·상담 경로를 제공한다.
  - 접수했다고 해서 환불이 실행되지는 않는다.
- Commerce :2238 `[팀 확인 필요]`: 상담 채널과 운영 시간, 첨부, 전달 사진 공개 여부, 안심번호 사용 여부.
- Commerce :2174: 고객센터 화면 구성. AI 상담은 필수 범위가 아니다.

**현황**
- `case-service` 의 `/cs-intakes` 는 운영자가 접수하는 경로이고, `/help-requests` 는 라이더의 도움요청이다.
- 고객이 직접 문의를 접수하고 처리 상태를 조회할 경로가 없다.
- 고객이 자기 주문의 전달 사진을 조회할 경로가 없다.
  - Commerce :192: 본인 주문인지 확인한 뒤에만 보여 준다.

**요청**
1. 고객 문의 접수 명령과 그 짝 조회. 담을 내용: 주문, 배송 건, 품목, 사유, 사진 참조, 멱등키.
2. 전달 사진을 고객에게 공개할지 결정하고, 공개한다면 조회 경로를 둔다.
3. 상담 채널(채팅/전화) 결정과 운영 시간·연결 상태를 주는 방식.
   - 팀 결정 전이면 "보류"로 회신해 주기 바란다. 클라이언트는 해당 기능을 막아 두고 주문 조회는 그대로 유지한다.

## BR-17 현금영수증 (낮음)
**근거**: Commerce :1771
- 현금영수증은 세 가지를 구분한다: 신청 정보, 실제 발급 가능 여부, 발급 결과 조회.
- 개인/사업자 입력 화면이 있다고 해서 모든 결제수단에서 발급할 수 있다고 안내하지 않는다.

**현황**: 계약에 현금영수증 관련 필드나 경로가 없다.

**요청**
1. 1차 범위인지 확인해 준다.
2. 1차 범위라면 다음이 필요하다:
   - 결제수단별 발급 가능 여부
   - 신청 명령(개인은 휴대폰, 사업자는 사업자등록번호 10자리)과 그 짝 조회
   - 발급 결과 조회

## BR-18 주문서 이탈 시 초안 처리 (낮음, 질문)
**근거**
- Commerce :109: 화면 이탈이나 제한시간 경과만으로 성공 거래를 실패로 간주하거나 확보를 해제하지 않는다.
- Commerce :1563: 앱에서 타이머만으로 점유를 해제하지 않는다.
- 계약: `Quote.quoteExpiresAt` 은 초안 생성 후 10분이다.

**현황**: `order-drafts` 에는 POST, GET, `/checkouts` 만 있고 초안 취소 경로가 없다.

**질문**
1. 고객이 주문서에서 뒤로 나갈 때 클라이언트는 아무것도 호출하지 않고 초안이 만료되기를 기다리면 되는가?
2. 아니면 명시적으로 초안을 취소해 확보를 해제하는 경로를 둘 계획인가?

**회신 전 클라이언트 처리안**
- 나갈 때 서버를 호출하지 않는다.
- 다시 들어오면 `GET /order-drafts/{draftId}` 로 견적과 확보 상태를 다시 검증한다.
- 만료됐으면 새 초안을 만든다. 결제 결과가 불명인 초안에는 새 결제를 시작하지 않는다.

## 참고: 요청하지 않은 것과 그 이유
- **알림 목록·이동 대상·읽음**: `notification-service` 의 `/me/notifications` 와 `Destination` 으로 충분하다. 푸시 토큰은 BR-09에서 따로 다룬다.
- **주류 성인인증**: Commerce :696 `[확정 정책]` 이 "자체 성인인증 화면 없음, 토스 결제 인증으로 통합"이다. 따라서 별도 경로를 요청하지 않는다. 결제 진입 정보는 BR-01에서 다룬다.
  - 검증 전에는 주류 신규 주문을 서버가 막는다(:845). 그 결과가 견적이나 초안 거절 사유로 내려오는지만 확인 부탁한다.
